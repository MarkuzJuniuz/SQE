the whole builder. Read from the code on 2026-10-16 (version v0.41.28 plus PR #65). **Nothing here was run in DCS**:
it is what the code says it does. When a note says "check", verify before acting on it. Line numbers drift, so
the notes name functions, variables and comments to search for. Keep this file current: when a PR changes
one of these behaviours, change the note in the same PR.

read the code, then correct the note and update its stamp. Stamps: `verified v0.41.28 + PR #65, 2026-10-16` unless a section says otherwise.

## 2. How a flight is built (outline)
_verified v0.41.54, 2026-10-21_

Since v0.41.54 `_spawn_flight` (mission_builder.py) is a list of stage calls; to change one part of a flight, go to its stage: route `_support_cap_route` / `_flight_route`; group `_make_group`; loadout, names, jammers `_dress_group`; engage circles, holds, ROE and range options `_engage_tasks`; seat, radio presets, AI frequency and fuel `_crew_setup`; manifest and radio calls `_announce`; ground-attack ROE `_roe_defaults`; each point's tasks `_attach_waypoints`; radar gate `_dead_gate`; recovery and landing `_home_leg`.

1. `engine.py` plans the day: objectives, packages, flights (role, aircraft, base, tag).
2. `mission_builder.py` builds each blue flight: waypoints (`plan_route` or the support-CAP branch), times
   (`assign_times`), group, then the tasks. AI flights and the all-AI test (`player_is_ai`) get the full set of tasks.
   The human player's flight skips most of them (the loop `continue`s after the player's ETA/name handling).
3. Group-level tasks go on `g.points[0].tasks` (they apply from the start). Waypoint-level tasks go on that waypoint.
4. Home leg: AI airfield flights add an `RCV` entry point (staggered by `RCV_SPREAD`), then land or are recovered by
   `SQE_RECOVER`; carrier flights are recovered `CV_RECOVER_NM` out; the player lands for real.

## 3. Flight classes: waypoints and tasks
_verified v0.41.50 (role rename), 2026-10-21_

Roles (`sqe/models.py`), one name per job since v0.41.50: CAS, CAP, TARCAP, ESCORT, SWEEP, SEAD, STRIKE.
- **TARCAP role** = a station short of the target (was `Role.ESCORT` before v0.41.50).
- **ESCORT role** = package escort (holds on a station, leaves after the last striker is off target; was `Role.SWEEP` in a strike / DEAD / CAS package).
- **SWEEP role** = Fighter Sweep (COUNTER_AIR package, `g.sweep`, waypoint action `SWEEP`) and the fleet-defence fighters.
- Waypoint action names follow the role since v0.41.60 (PR B): `TARCAP`, `ESCORT`, `SWEEP` (the Fighter Sweep station was `SWEEPSTN`; the old `SWEEP` action of the package escort is now `ESCORT`). A *station* is a waypoint that orbits (`w.orbit`) or a TARCAP's own point; stations are not time-locked, a flight with no station (stand-off setting off, fleet-defence fighters) flies its ESCORT / SWEEP point to a time (`_set_eta`). There are no per-job flight classes; the job code lives in the mixins (`strike_tasks.py`, `fighter_stations.py`, `support_caps.py`, ...). `plan_route` still tests `(Role.ESCORT, Role.SWEEP)` together in the places where both fly a station.
- Saved campaigns: format 6; `state._migrate_roles_v6` converts format-5 plan flights (ESCORT -> TARCAP; SWEEP -> ESCORT unless the objective is COUNTER_AIR / FLEET_DEFENSE).
- Tankers and AWACS (v0.41.87, verified 2026-10-21) are assets: `sqe/support_assets.py` (`TABLE`, `state.support_assets`, `windows`, `plan`, `up_for`, `lose`, `step`). `PackageBuilder._support` keeps only the entries that are on orbit while the package flies (`engine.plan_day` recomputes it once the start times are known); the mission builder records each support aircraft in the manifest (`kind` `support`) and `apply_debrief` takes a shot-down one off its asset.
- Support CAPs are flights with a `tag`: HAVCAP, BASECAP, CVCAP, TNKCAP (not a separate role). None of the four are package slots now (HAVCAP and TNKCAP since v0.41.88, BASECAP and CVCAP since v0.41.85; verified 2026-10-21): `blue_barcap.plan` plans them each day from the BARCAP areas (saved in `state.barcap["blue_flights"]`, coverage in `blue_cover`), pays them out of `daily` before the packages (`engine.plan_day`), and `blue_barcap.attach` gives each package the planned sortie of the area facing its target that is up while it flies (same callsign in every package that carries it; merged missions build it once, `_gather_support`). HAVCAP / TNKCAP are chains per support asset (`blue_barcap._plan_guards`, `GUARDS`, along `support_assets` windows, 2 h pairs, never the player's squadron), attached to packages that carry that AWACS / tanker.

## 4. The fuel model
_verified v0.41.28 + PR #65, 2026-10-16_

- Setting `ai_unlimited_fuel` (default True): "Retribution-style", unlimited until the push, real over the combat leg,
  unlimited again from egress.
- Implementation: `SetUnlimitedFuelCommand(not past_push)` on `points[0]` (blue AI flights only);
  `SetUnlimitedFuelCommand(False)` inserted at the waypoint named **PUSH** or **CAP1**;
  `SetUnlimitedFuelCommand(True)` inserted at the waypoint named **EGR**.
- Consequence: the "free again" step hangs on the **EGR waypoint existing**. Classes with no EGR never get it back.
- `past_push`: for a flight already underway (an earlier package folded in; `in_progress`), the start is real fuel.

## 5. Questions answered so far
_verified v0.41.28 + PR #65, 2026-10-16_

**Which classes set their waypoint actions?** See section 3. Actions come from `plan_route` (`routes.py`): `HOLD` (MSHL),
`CAPORBIT` (CAP1), `TARCAP` / `ESCORT` / `SWEEP` (stations), `BOMB`, `SEAD`, `JSOW`, `CAS` (attack points).
The builder turns them into DCS tasks (orbit with `stop_after_time`; v0.41.44: station orbits are `Circle`, because DCS's default Race-Track runs from its waypoint to the NEXT waypoint, which for a station is RTB (2026-10-20 tracks); only the support-CAP CAP1 -> CAP2 racetrack is a real race-track; `AttackGroup`, `Bombing`, ROE, ECM, fuel).

**Would the CAPs still have unlimited fuel on the way home, now that they lost the egress waypoint?** No.
Support CAPs, TARCAPs and Fighter Sweeps have no EGR (stand-off fighters were given none in v0.40.1: they go home from
their station). The fuel switch to real happens at PUSH or CAP1, and only EGR switches it back, so those jets fly
home on real fuel. Escorts keep it only when the egress leg was clear of SAM cover. What saves them today is the
bingo RTB (`OptRTBOnBingoFuel`) and the hold times. A jet that leaves its station low could still run dry on the way home.
Flame-outs happened in earlier runs (v0.41.8, v0.41.14); the fix then was the bingo RTB, and whether the no-EGR fuel state
contributed has not been checked. Possible fix, not built: a
`SetUnlimitedFuelCommand(True)` on the first waypoint after the station (or the RCV point) for classes with no EGR.
Whether that is wanted is XO's call (a CAP that stays on real fuel at the end of its time is also "more honest").

## 6. Scrambles and reactive spawns
_verified v0.41.28 + PR #66, 2026-10-16 (read from the code, not run; the emergency-scramble paragraph also read from a test .miz; v0.41.121 and .122 bullets added 2026-10-23)_

Three kinds exist, all built in `mission_builder.py` (`_spawn_enemy`-style block near the red alert code, and `_spawn_reactive`), planned in `sqe/reactive.py`:
- **Alert / scramble start types** (`_alert_group`, v0.41.80): default = hidden (late-activated) and put on the runway by the hook ALERT_TAXI_S after it is called (`_rwyq`). With the setting `hot_ramp_scrambles` (off by default) a pair at a LAND field with parking for its type instead starts `StartType.Warm`, `uncontrolled`, and a trigger pushes `StartCommand` when called (`how == "ramp"`; relief / standby pairs called by a hook flag use `_call_by_flag`). Never at the player's own field, never at a carrier (hidden deck start), fallback = the hidden runway start when the field has no parking. Ruins rule (hot on the runway where a field has ruins) not done. Verified v0.41.80.
- **Red alert pairs** (on the runway or ramp, `_alert_group`): a trigger zone round the field (`_field_zone`, `FIELD_DETECT_NM`; +`RAMP_LEAD_NM` 30 nm when `hot_ramp_scrambles` is on, v0.41.92: ramp pairs took 5 to 9 minutes call-to-air in XO's runs) fires when blue is detected inside it; on CAS days a clock replaces the zone (friendly troops sit on the target). Route (v0.41.91, verified 2026-10-21): the start, one `INTERCEPT` waypoint at the station from `scramble.red_station` (the target if a live red SAM covers it, else the covered point nearest the target on the line from its field, else 15 nm out from the field) with an orbit until TOT + 1 h, then a landing (`_land_home`, also on Bandit / Relief / Standby). No other SAM-bending; `_limit_engage(g, enemy_cap_engage_nm)`.
- **Red reinforcements** ("Reinforce k"): the same shape, plus a random delay; `reactive.plan_red` picks fields within the type's `INTERCEPT_NM`, held to a ratio of blue fighters.
- **Blue alert pairs** (`reactive.blue_sources`, carrier or field): trigger zone of 120 nm round the target (fleet / raid objectives) or a clock for other targets; route (v0.41.91, verified 2026-10-21): one `CAP` waypoint at the station from `scramble.blue_station` (forward of the target toward where the raid comes from, up to 30 nm, under our own field air defence and clear of red's SAM rings; else on the target) with an orbit for `cap_minutes`, engage limit `friendly_cap_engage_nm`, then land or RTB.
- Red patrols (planned picture, `CAP1`/`CAP2`) are different: they have a station and a circle (`A2A_ZONE_NM`) like ours.

**Red SEAD pair (v0.41.84, verified 2026-10-21):** a Su-24M land raid on a field with a live Patriot / HAWK may carry `extra["arm"] = 2` (`PackageBuilder._land_raid_plan`, odds `Difficulty.raid_arm`). `RaidSpawns._spawn_raid_arm` builds group "Raid SEAD 1" (Kh-31P, `loadouts.enemy_arm_loadout`): same way in as the bombers, `AttackGroup` ARM on the field's Patriot group (`MissionBuilder.base_ad`, filled in `_place_base`) from `ARM_LAUNCH_NM`, `ARM_LEAD_S` before the bombers' TOT. Unflown raids: `raids.overnight` halves the battery cover (`ARM_AD_FACTOR`).

**Gap (found 2026-10-16; the blue and red alert stations use `scramble.py` since v0.41.91, reinforcements the red one; the rest below still holds for them):** none of the three scramble kinds use the SAM rules (`avoid_circles`, `_zone_sams`, `_cover_circle`, `_clear_zone`). They fly a straight line to the target and orbit on it. For blue alert pairs that target can be inside a red SAM's reach. Raids by red bombers are separate (`raids.py` has `shy`, `PATRIOT_NM`, `HAWK_NM`).

**Emergency raid scramble and merging (read 2026-10-16 from the code and XO's Kobuleti test .miz; the test ran with `RAID_SCRAMBLES = True` only):**
- The emergency package is built directly in `_make_emergency` (engine.py) and never goes through `flyable()`, so `FLEET_DEFENSE` can stay in `AI_ONLY`; the one switch is `RAID_SCRAMBLES` (engine.py top).
- Blue scramble flights have `CAP1` exactly on the raid's target, so they orbit over the base (inside SA-10 reach in the test; 6 of 7 blue losses went to the Sukhumi S-300).
- Red raid groups (bombers and escorts) are placed in the AIR at t=0, about 93 km (50 nm) from the target, at 12,000 ft, 232 m/s, with waypoints start, STN, STN, BASE: no field spawn, no marshal, no TOT. Colt 3 / Dodge 3 are clock-activated (`c_time_after` 161 / 196 s); Viper alert pairs launch from the runway when the zone trigger fires (10 s in the test).
- Nothing folds into a raid scramble: `_pkg_xy` returns None for `BARCAP` / `FLEET_DEFENSE`, so `merge_center` is None and `merge_candidates` returns []. Only a CAS emergency folds packages in (`lead_extras`). Taking the scramble sends the package you were tasked with to the war sim (`fly`, "left to the other squadrons"), or postpones it a day (`_postpone_if_short`).

## 7b. How red picks targets (raids and the carrier)

## 8. Mission Editor refuses the mission: waypoint lock errors
_verified v0.41.32 + PR #74, 2026-10-16 (read from the code; FIXED, confirmed by script, not yet reopened in the Mission Editor by XO)_

The Mission Editor (ME) validates every route on load/save. Messages seen so far, all about the speed and time padlocks on a waypoint:
- "All waypoints (5-5) have locked speed and surrounded by waypoints 4 and 5 with locked time" (v0.41.2; fixed by not time-locking fighter stations). Same family: v0.8.5 "(2-4) ... waypoints 1 and 4".
- **"Waypoint 8 have both unlocked speed and time and not surrounded by waypoints with locked time!"** (XO, 2026-10-16, "Viper 2"). The mirror rule: a point whose speed AND time are both free needs a time-locked point on each side. **Fixed in v0.41.32 (PR #74).**

How SQE sets the locks (search `_set_eta`, `_free_locked_speeds`, `speed_locked`, `ETA_locked`, `_trailing_steerpoints` in `mission_builder.py`):
- Time-locked: the first point (takeoff, `ETA = 0`), PUSH, and the objective point (not stations). Speed is locked everywhere except between PUSH and the objective, and on the point just before PUSH.
- `_free_locked_speeds` frees the first speed in any run of speed-locked points between two time-locked ones, and (v0.41.32) also locks the speed of any point past the LAST time-locked waypoint that would otherwise be both-unlocked.
- `land_at()` (pydcs) leaves a flight's landing point `speed_locked = True` by default; that is safe on its own.
- **Confirmed cause of the "Viper 2" error (not a hypothesis any more):** `_spawn_flight` used to force the player's own landing point `speed_locked = False` ("your landing point: speed free, so it never closes a locked-speed run" — a leftover from the v0.41.2 fix above, which only applies when a locked-time point actually follows). `_trailing_steerpoints` (package-level, runs after every flight is built) then appends DIVERT/TKR/BULLS reference points on the player's own route — none of them time-locked (`add_waypoint` always sets `ETA_locked = False`). So the landing point was never followed by a locked-time point, and the override broke the mirror rule. Reproduced on every player flight with trailing steerpoints (not just raid scrambles): the override line is gone, and `_free_locked_speeds` now covers the tail generically instead.

Quick workaround for XO in the ME on a mission generated before v0.41.32 (no rebuild): open the flight's waypoint named in the error and lock its speed (padlock beside speed), or lock its time (padlock beside ETA), then save. Not needed on builds from v0.41.32 on.

How to check a mission without the ME: unzip the `.miz`, parse `mission` with `dcs.lua.loads`, and for each point in a group's route check `not ETA_locked and not speed_locked` with a locked-time point bracketing it on both sides (not just "both false" — a bracketed point like MSHL, between TakeOff and PUSH, is fine). `tools/smoke_test.py`'s raid-build check (`_bad31`, builds a real player flight, not the AI test) does exactly this now. Ask XO for the `.miz` if the ME still refuses a mission after v0.41.32; it would mean a new code path adds points after the last time-locked waypoint.

- While sunk everything that plans with the boat asks `fleet.carrier(state)` (None while sunk) or `fleet.is_sunk_base`: `bombers._carrier`, `war` (bomber call), `packages._raid_plan`, `blue_barcap` (the CVCAP fallback), `barcap` (rings, areas), `sweep._home_guess`, `support_assets.plan` (the boat's E-2C / S-3), `carrier_hit.deck_factor` (0.0), `mission_builder._place_base` (no ship; sunk escorts skipped by index).
- Defeat: `ground.fallen_count` = fallen fields + `fleet.counts_as_fallen` (1 while sunk); `posture` and `overview_detail` print the status.
- A squadron of Navy jets on a land field: `packages._support` (AWACS, tanker), `assign_player` (the catapult limit), `mission_builder._rtb_note` and `briefing` (recovery line) read the squadron's base, not `AIRCRAFT[...].home`.
- Open: the escort ships are three fixed slots (cruiser, destroyer, frigate) in `_place_base`; the hook's ship death names are read from XO's state file, not yet from a run with this build.

## 18. Road sites belong to the side their road connects to (v0.41.258, verified 2026-11-03)
- Where: `sqe/road_front.py` (`routes`, `route_sides`, `site_side`, `field_side`, `cut_side`); used by `road_sites.build` (owner at the campaign start) and `road_sites.flip` (called from `ground.resolve_day` after `check_falls`).
- Rule: the front is a cut across the shipped road net at `g["line_km"]` (`ground.path_pos`: km along the sector centres, km sideways; larger km = the Blue end). Road points within `CORRIDOR_KM` 60 of the line of sectors are on the cut's side; the two ends of each route have the side of the nearest airport (`th["road_blue_airports"]`); other points take the nearest anchor along the road. A site takes the side of the nearest road stretch within `SNAP_M` 3 km, else the cut, else the nearest airport.
- flip: a site whose road side is not its pool's side changes pool (`ground._move_sites`, the id stays, so the Overview prints "(captured)"); the red battalion (`guards` = the site) gets health 0; `g["road_flips"]` logs each. No margin, no cap. Not seen in DCS.

## 20. Parked jets, Standoff Strike and the JDAM release point (v0.41.297 to .299, verified 2026-11-05)
- **Parked jets** (`mission_builder._spawn_parked_jets`, `_ramp_xy`): a counter-air strike (not the Sweep) finds the target field's jets as static aircraft on free parking spots: per type the wing's serviceable jets minus the jets the mission launches from that field, up to `PARKED_MAX` 12. The strikers aim at the ramp (`_jitter_primary`). A destroyed one comes off the wing as an `enemy_air` group marked `parked` (debrief `w.lose`). Not verified in DCS: whether the hook counts a destroyed static dead.
- **Standoff Strike** (planner v0.41.298, builder .299): `war.ObjectivePlanner.plan` turns a supply strike (FUEL / DEPOT, no gate SAM, no `after`) into `STRIKE` aim `STANDOFF` when `STANDOFF_MIN_DEF_FLIGHTS` (4) red fighter flights reach it and a Hornet squadron has 2 jets. `packages._slots`: `Slot(STRIKE, 4, kit="SLAM")` + the usual TARCAP / escort; `KIT_JETS` says which airframes fill a kit slot; no Hornet free = the job waits (`NoPlayerSlot`). Loadout kit `SLAM` (AGM-84H x2, `loadouts._D["FA-18C"]`). War sim: red's fighter cover counts `STANDOFF_AIR_FACTOR` 0.5. No fighters-clear gate (`strike_tasks`, `air_only_`).
- **Release points** (`routes.plan_route(rel=...)`, `StrikeTasks._rel_kind` / `_flight_profile`): `rel="SLAM"` puts a `SLAM` waypoint `SLAM_LAUNCH_NM` (120, clamped to 0.8 of the route minus 6; `Geometry.launch_nm`, set in `_flight_plans`) out from the target, IP 6 nm before it; `rel="JDAM"` puts a `REL` waypoint `JDAM_RELEASE_NM` (8) short of the target for AI strikers of `JDAM_JETS` on strikes and counter-air strikes (not RUNWAY, not Close DEAD, not a person's flight). Both: action `BOMB`, `Wpt.aim` = the target (the bomb task is aimed there, `_bomb_task`), then the JSOW pattern's egress back along the approach. JDAM / SLAM flights are planned with a derived profile (`dataclasses.replace`: strike altitude `JDAM_ALT_FT` 30,000, `no_low`); the tier table is keyed on that profile, so every `plan_route` call for such a flight must pass `self._flight_profile(f, package)` (`_launch_points` does). Escorts of a SLAM package are stationed behind the launch point by the JSOW shepherd branch (`kit in ("JSOW", "SLAM")`).
- **Sources / unknowns:** JDAM release range from DCS players' tests (9.3 nm at 30,000 ft, 12.5 nm at 33,000 ft) and GlobalSecurity (about 15 miles); the AI's actual release point and whether it fires a SLAM-ER on a `Bombing` task are untested in DCS.
